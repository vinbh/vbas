---
name: User prefers polish per milestone
description: When given the option to ship a milestone barebones vs add UX polish before moving on, user picks polish — offer polish steps proactively
type: feedback
---

When a milestone hits "minimum viable" the user has consistently chosen to invest in UX polish before advancing to the next milestone, even when offered a fast-track option:

- M2 base shipped → user accepted the cyan ▍ bar + branded "vbas" footer offer instead of moving on to M3.
- That same M2 → user accepted the type-to-filter offer (separate UX improvement) instead of moving to M3.

**Why:** They want the project to feel polished and "catchy" (their word — also used when asking for a better README). Volume of features matters less than each feature feeling complete and distinctive.

**How to apply:** When wrapping a milestone, default to listing 1–2 concrete polish ideas and asking "polish first or move on?" — rather than reflexively pitching the next milestone. Keep the polish offers concrete and small (not vague "we could do X someday"); they say yes when the offer is well-scoped. Small polish items in this project's vein: type-to-filter, branded visuals, position indicators, descriptive empty states, key-hint footers, error-on-cancel-vs-no-match disambiguation.
